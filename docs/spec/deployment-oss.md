# Деплой и OSS-обвязка

Читаемое зеркало спеки `deployment-oss`.

## Production-артефакты

Репозиторий несёт готовые к продакшену артефакты деплоя: systemd-юнит `deploy/gatekeeper.service` и `deploy/Dockerfile` для статического Go-бинаря без cgo. Рядом — документация о том, как прогнать миграции до запуска основного бинаря.

`deploy/gatekeeper.service` подхватывает конфигурацию из внешнего файла через `EnvironmentFile=`, задаёт стабильный `WorkingDirectory` рядом с SQLite-базой, рестартит сервис при падении (`Restart=on-failure`) и работает под выделенными непривилегированными `User=`/`Group=`. Секреты бота и провайдеров в самом юните не лежат — они приходят из env-файла.

`deploy/Dockerfile` — multi-stage: сборка статического бинаря с `CGO_ENABLED=0`, рантайм-стадия на минимальном/distroless-образе. Энтрипоинт контейнера — бинарь `gatekeeper`; cgo в рантайме не требуется. Рантайм-секреты передаются через переменные окружения, а не запекаются в образ.

## Порядок миграций

Миграции выполняются отдельным шагом до старта сервиса: оператор запускает `migrate up`, и только потом — `gatekeeper`. Немигрированная база — это ошибка старта, а не повод для тихой автомиграции основным бинарём.

## README: quickstart для self-hosting

`README.md` даёт англоязычный quickstart, которого достаточно, чтобы поднять бота без чтения полной продуктовой спеки. Он покрывает установку, конфигурацию через переменные окружения, миграции, запуск бота и четыре Telegram-чата (Boosty-группа, Tribute-канал, клубный чат, клубный канал) с их ID. README объясняет, зачем боту админ-права `can_invite_users` и `can_restrict_members` на управляемых ресурсах, как выбирается `TRIBUTE_MODE`, и приводит чек-лист ручной проверки развёртывания.

Раздел про бэкапы разъясняет особенности SQLite в режиме WAL: использовать `VACUUM INTO` либо остановить бота перед копированием базы; при копировании «живых» файлов — захватывать sidecar-файлы `-wal` и `-shm` или сначала сделать checkpoint. Копии бэкапов трактуются как секреты.

Known limitations перечисляет основные ограничения v1 и trade-off'ы режимов: лаг Boosty до ~4 недель, отсутствие полного списка участников Telegram, поведение kick'а, способное удалять сообщения, и опциональность webhook-режима Tribute.

## OSS-метаданные и security-процесс

В репозитории присутствуют:

- `LICENSE` с условиями MIT;
- `CONTRIBUTING.md` — команды сборки, тестов и линта, ожидания по стилю, а также шаблон добавления нового `Source` (источника подписки);
- `SECURITY.md` — как сообщить об уязвимости приватно, без публичного раскрытия секретов, с предупреждением не включать токены бота, ключи провайдеров и invite-URL в публичные issue.

Эти файлы не содержат маркеров generated-by/vendor-атрибуции, секретов или реальных токенов.

## CI

GitHub Actions workflow `.github/workflows/ci.yml` запускается на push и pull request и выполняет канонические команды сборки, тестов и линта из `Taskfile.yml`. Реальные учётные данные Telegram или Tribute не нужны: тестовая конфигурация использует фейковые значения или изолированные временные базы, поэтому build/test/lint проходят и в форке, и без репозиторных секретов.

## Поведение

- systemd-юнит указывает на внешний env-файл и сам не хранит секретов бота/провайдеров.
- Docker-образ собирает статический рантайм с бинарём `gatekeeper`; конфигурация — через переменные окружения.
- Порядок развёртывания: `migrate up`, затем `gatekeeper`; немигрированная база — ошибка старта.
- По README оператор находит ID Boosty-группы, Tribute-канала, клубного чата и клубного канала и понимает требуемые админ-права бота.
- По README-бэкапам оператор не копирует только основной SQLite-файл из живой WAL-базы без checkpoint'а или копирования sidecar-файлов.
- README фиксирует основные ограничения v1 и trade-off'ы режимов до выхода в продакшен.
- `LICENSE` объявляет условия MIT.
- В `CONTRIBUTING.md` находятся канонические команды build/test/lint и паттерн добавления нового источника подписки.
- `SECURITY.md` описывает приватный канал репорта и запрещает класть в публичные issue токены, ключи и invite-URL.
- На открытие pull request CI гоняет build, test и lint.
- В форке и без репозиторных секретов build/test/lint всё равно отрабатывают на фейковой тестовой конфигурации.
