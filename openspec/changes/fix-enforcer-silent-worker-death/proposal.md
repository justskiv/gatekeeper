# Fix silent enforcer worker death on request timeouts

## Why

2026-08-15 в 23:47 UTC оба воркера outbox-пула вышли молча, и бот проработал
9.5 часов с мёртвым пулом, рапортуя `healthy`. Reconcile продолжал ставить в
очередь ~184 задачи в час, разгребать их было некому: к моменту обнаружения в
очереди лежало 1845 действий. Ни одна строка лога, ни healthcheck, ни `/readyz`
отказа не показали.

Причина — `isContextDone(ctx, err)`: он считает завершением работы **любую**
ошибку, в цепочке которой есть `context.DeadlineExceeded`, не глядя на
состояние ctx. Клиент Telegram живёт с `http.Client{Timeout: time.Minute}`, а
таймаут `Client.Timeout` в `net/http` реализует `Is(context.DeadlineExceeded)`.
Флап Telegram API 15 августа дал такие таймауты — и обычный сбой запроса стал
неотличим от штатной остановки. Дальше по цепочке: `runOnce` вернул ошибку мимо
`handleFailure`, оставив действие в `running`; `runWorker` вернул голый `nil`
без лога; `Enforcer.Run` увидел, что все воркеры завершились, и вернул `nil`;
`errgroup` не отменил ничего, поэтому поллер и reconciler остались живы.

Тот же дефект скопирован байт-в-байт ещё в трёх файлах (`reconcile/reconciler.go`,
`reconcile/cleanup.go`, `telegram/poller.go`). Поллер уцелел **случайно**: его
`GetUpdates` идёт через собственный `rawRequest`, где transport-ошибка
оборачивается через `%s`, что рвёт цепочку `errors.Is`. То есть форматный глагол
работает необъявленной защитой, и её снятие без починки предиката уронило бы
весь транспорт Telegram, а не только outbox.

Отдельно вскрыта гонка, не связанная с инцидентом, но лежащая на том же пути:
lease длится 2 минуты, а действие может содержать несколько последовательных
Telegram-вызовов по 60 секунд каждый, то есть пережить собственный lease. После
этого `LeaseReady` отдаёт строку второму воркеру, а `MarkDone`/`Retry`/`MarkDead`
пишут `WHERE id = ?` без проверки владения — оба воркера исполняют действие и
оба записывают результат.

## What Changes

- **Граница остановки определяется только состоянием контекста.** Предикат
  `isContextDone` удаляется во всех четырёх пакетах, его место занимает
  `ctx.Err() != nil`. Личность ошибки при этом решении не опрашивается никогда.
- **Таймаут запроса становится обычной retryable-ошибкой** и уходит в
  `handleFailure` — с backoff, счётчиком попыток и переходом в `dead` по
  исчерпании, как любая другая сетевая ошибка.
- **Транспортные ошибки классифицируются.** В `internal/telegram` появляются
  категории `timeout` и `canceled` и предикаты `IsTimeout`/`IsTransient`.
  `rawRequest` начинает оборачивать transport-ошибку через `%w`, сохраняя
  цепочку; токен вычищается из `*url.Error` точечно, а не затиранием текста.
- **Lease получает fencing.** Терминальные переходы (`MarkDone`, `Retry`,
  `MarkDead`, новый `ReleaseLease`) выполняются только владельцем lease и только
  из ожидаемого статуса. Схема не меняется: маркером владения служит значение
  `locked_until`, полученное при захвате.
- **Воркеры супервизируются.** Каждый выход воркера логируется с причиной,
  воркер перезапускается с backoff, а устойчивая невозможность его удержать
  эскалируется в возвращаемую ошибку. `Enforcer.Run` MUST NOT возвращать `nil`,
  пока его контекст жив.
- **Незавершённое при остановке действие возвращается в очередь** без списания
  попытки, вместо ожидания истечения lease.

## Capabilities

### New Capabilities
- (нет)

### Modified Capabilities
- `outbox-enforcer` — остановка определяется контекстом, а не ошибкой; таймаут
  ретраится; терминальные переходы fencing-защищены; lease освобождается при
  остановке.
- `runtime` — Enforcer супервизирует воркеров, логирует каждый выход и не может
  вернуть `nil` при живом контексте; тот же запрет распространён на поллер и
  reconciler.
- `telegram-transport` — введены категории `timeout`/`canceled`; `rawRequest`
  сохраняет цепочку ошибок при вычищенном токене.

## Impact

- Код: `internal/enforcer` (`enforcer.go`, `ports.go`), `internal/telegram`
  (`client.go`, `poller.go`), `internal/reconcile` (`reconciler.go`,
  `cleanup.go`), `internal/store/outbox.go`.
- Схема БД не меняется. Fencing использует существующую колонку `locked_until`.
- Конфигурация не меняется: политика перезапуска воркеров задана константами
  пакета и не выносится в env.
- Поведение при остановке процесса меняется в лучшую сторону: действие,
  прерванное на середине, возвращается в `queued` сразу, а не через 2 минуты.
